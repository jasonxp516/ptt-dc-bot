# 期末專題企劃書：PTT 智慧二手交易追蹤與多平台即時推播機器人（PTT-DC-Bot）

**專題名稱**：PTT 智慧二手交易追蹤與多平台即時推播機器人 (PTT-DC-Bot)  
**英文名稱**：PTT-DC-Bot: An Intelligent PTT Marketplace Monitoring and Multi-Platform Notification System  
**專案類別**：分散式爬蟲、自然語言處理（LLM）、微服務與多平台通訊整合  
**文件版本**：v1.1.0 (Production Release)  

---

## 摘要 (Executive Summary)

PTT（批踢踢實業坊）為台灣歷史悠久且活躍度極高之匿名網路社群，其中包含 `HardwareSale`（電蝦二手）、`MacShop`（蘋果二手）、`nb-shopping`（筆電交易）等看板，每日擁有數千則二手電子零件與消費性硬體交易貼文。然而，現存之開源推播工具（如傳統 Webhook 腳本、RSS 訂閱器、PttAlertor）多僅仰賴粗糙之標題關鍵字比對與單向廣播，導致使用者長期面臨「點擊通知才發現早已售出」、「合售貼文因單一品項售出而遭全篇忽略」、「硬體規格數字被誤判為售價」以及「高頻爬取引發 PTT 503 限流」等痛點。

本專案開發之 **PTT-DC-Bot** 是一套結合**確定性規則引擎**與 **Groq 大型語言模型（LLM）語意推理**之非同步看板監控與多平台即時推播系統。系統具備三大核心突破：
1. **純函式售出狀態機與 18 小時原位更新（In-Place Edit）**：持續追蹤文章簽名檔後之作者推文，售出時自動於 Discord / Telegram 原始卡片劃上刪除線，徹底避免洗版。
2. **多品項獨立虛擬視角切分（Virtual Item Slicing）**：合售貼文依關鍵字切分獨立狀態與價格解析，精準過濾預算上限並消除型號干擾。
3. **Crawl-Once, Fan-Out 高效架構與多平台派發**：單次抓取全租戶共享快取，支援 Discord（原生 `/setup` UI、Slash 指令）、Telegram（長輪詢、行內鍵盤）與 Email SMTP（響應式 HTML、防標頭注入）。

系統採用 SQLite WAL 實現多租戶資料隔離，並已通過 250 項單元與整合測試，在 80 筆真實樣本評測中達到 100% 售出判定準確率，具備高度之工程完整性與實用價值。

## 1. 研究背景與動機 (Background & Motivation)

### 1.1 背景說明
台灣的二手 3C 與電腦硬體交易市場中，PTT 佔有舉足輕重的地位。許多高性價比之二手商品（如顯示卡、筆記型電腦、智慧型手機）上架後往往在數分鐘內甚至數秒內即由買家寄信洽談。因此，具備即時推播能力的自動化追蹤工具成為二手買賣雙方之剛性需求。

### 1.2 現有方案之缺陷與挑戰
經深入分析市面既有之 PTT 監控方案，發現存在下列關鍵瓶頸：

| 現有方案類型 | 典型代表 | 核心缺陷 |
| :--- | :--- | :--- |
| **簡單 Webhook 腳本** | 自寫 Python/Node.js 爬蟲 | 單向廣播、無售出追蹤、硬編碼配置難以維護、容易因未控管頻率遭 PTT 封鎖。 |
| **通訊軟體機器人** | PttAlertor 等早期開源專案 | 僅能單純比對標題關鍵字，無法辨識合售文章，且缺乏預算與硬體型號消歧義機制。 |
| **RSS 訂閱工具** | 普遍 RSS Reader / Discord Webhook | 受限於 RSS 來源之快取延遲，推播嚴重滯後，且無法在文章售出後進行回溯修改。 |

### 1.3 核心痛點整理
1. **過時無效通知（Dead Notifications）**：賣家常於內文或推文更新「已售出」、「洽中」，傳統機器人無法偵測，導致買家耗費時間點入已結案之文章。
2. **多品項合售文誤判（Multi-Item Collision）**：例如標題為 `[賣/台北] 1060已售出/3060Ti/電供`，傳統系統因偵測到「已售出」而全篇過濾，使欲購買 3060Ti 之買家錯失訊息。
3. **規格型號誤判為售價（Model-Price Confusion）**：標題中的硬體型號（如 `RTX 3060`、`12G`、`750W`、`i5-12400`）極易被正則表達式誤擷取為商品售價，導致預算過濾機制失靈。
4. **社群與個人隱私衝突**：現行機器人多只支援公開頻道推播，一般使用者無法建立不公開之私人追蹤清單。

## 2. 專案目標與預期成果 (Project Objectives)

本專案旨在打造一個**低延遲、高準確、零營運成本且兼顧隱私與跨平台**之智慧推播系統，達成以下具體目標：

1. **研發高精準度狀態引擎**：建立多維度售出判定模型，涵蓋「標題標籤」、「內文段落」與「作者簽名檔後最新推文」，並透過 LLM 進行語意複審，降低偽陽性與偽陰性。
2. **實現多租戶原位訊息更新**：推播後建立持續追蹤佇列，當狀態轉移至已售出時，直接透過通訊協定 API 編輯已發布之訊息卡片，保持頻道清爽。
3. **構建 Crawl-Once, Fan-Out 高效快取架構**：以看板為單位聚合爬蟲請求，全域共享文章本體與 AI 判定快取，並透過優先級佇列保護互動性操作。
4. **支援三大主流通訊平台**：一次開發同時覆蓋 Discord、Telegram 與 Email SMTP，讓使用者依情境自由配置推播管道。
5. **落實企業級安全與容器化部署**：實作 Prompt Injection 防禦、RBAC 權限控管、SQLite WAL 資料庫管理、心跳式 Docker 健康檢查與 CI/CD 自動化發行。

## 4. 關鍵演算法與創新機制 (Key Mechanisms & Innovations)

### 4.1 純函式售出狀態機（Sold State Machine）
為徹底解決推文誤判問題，本專案將判讀邏輯自爬蟲抽離為獨立無副作用之純函式引擎：
1. **地名與時間過濾**：導入遮蔽規則，排除「可洽中壢站」、「高雄車站面交」、「結標時間」等包含「洽」、「結」字樣之非售出詞彙。
2. **作者簽名檔穿透**：將文章切分為「標題」、「正文」與「簽名檔後推文」。推文中僅有作者本人發表的推文（含 `推`、`→`）具備標記售出之權限，買家之詢問推文（如「排」、「已信」）均不影響商品狀態。
3. **四態精細分類**：
   - `SOLD`：確認已售出（標題變更或作者推文「已售」、「售出」）。
   - `RESERVED`：暫停出售中（「暫售」、「洽中」）。
   - `NO_MAIL`：不再接受信件（「勿來信」、「信件過多」）。
   - `AVAILABLE`：仍在架上可供購買。

### 4.2 多品項合售獨立切分（Virtual Item Slicing）
當賣家同時販售多項物品時，系統透過 `apply_keyword_view` 演算法：
- 掃描全文並依據關鍵字位置定位所屬品項區塊。
- 獨立擷取該品項之售價（排除型號干擾）與售出狀態。
- 分別向不同關鍵字訂閱者推送專屬視角卡片，實現單篇貼文多品項精確追蹤。

### 4.3 優先級調度與動態負載池（Groq Dynamic Pool）
為在免費 API 額度限制下達到最佳體驗，系統設計了三模型動態輪替機制：
- 聚合 `openai/gpt-oss-120b`、`qwen/qwen3.8-27b` 與 `openai/gpt-oss-20b`，將每分鐘 Token 吞吐量自單一模型 8,000 TPM 擴充至 24,000 TPM。
- 劃分 P0（即時對話）至 P3（背景維護）四級優先佇列。當系統負載過高時，排程器自動降速或丟棄背景批次任務，優先保障終端使用者之互動流暢度。

### 4.4 縱深防禦架構（Security Hardening）
- **Prompt Injection 防禦**：所有來自 PTT 之非信任資料一律以 `wrap_untrusted` 進行 XML 標籤轉義並封裝於 `<untrusted_ptt_content>`。
- **意圖鎖定門禁（Intent Guard）**：AI 代理調用寫入工具（如刪除規則、變更頻道）前，必須通過正則詞界與目標參數比對，杜絕惡意貼文誘騙 AI 篡改設定。
- **動態權限再驗證**：在推播發送前再次校驗使用者是否具備伺服器管理權限，防止權限遭收回後繼續外洩訊息。

## 5. 跨平台能力評估與實作 (Cross-Platform Evaluation)

專案針對主流通訊管道進行了深度技術與成本調研：

| 評估維度 | Discord | Telegram | Email (SMTP) | LINE (受限不支援) |
| :--- | :--- | :--- | :--- | :--- |
| **連線機制** | 出站 WebSocket Gateway | 出站長輪詢 (Long Polling) | 出站 TCP (Port 587/465) | 入站強制公網 HTTPS Webhook |
| **通訊成本** | 完全免費 | 完全免費 | 完全免費 (Gmail / 自建) | 每月僅 200 則免費，超額月費 NT$800 起 |
| **雙向互動** | Slash 指令、按鈕、Modal | 文字指令、行內鍵盤按鈕 | 僅單向通知 | 需額外架設 Webhook 伺服器 |
| **售出原位更新** | **支援** (`edit_message`) | **支援** (`editMessageText`)| 不適用 (郵件送達不可竄改)| 不支援 (需重複發送推播扣額度) |
| **NAT/防火牆穿透**| 隨開即用，免公網 IP | 隨開即用，免公網 IP | 隨開即用，免公網 IP | 需固定 IP、網域、SSL 憑證 |

**結論**：系統正式實作支援 Discord、Telegram 與 Email 三大管道；LINE 因 LINE Notify 終止服務且 Messaging API 成本與架構限制，評估後不予納入。

## 8. 專題結論與未來展望 (Conclusion & Future Work)

### 8.1 成果總結
PTT-DC-Bot 成功融合傳統規則引擎的高效率與大型語言模型的語意推理能力，有效解決了多年來 PTT 二手買賣社群常見的過時推播與誤報痛點。在軟體工程面，專案落實了分層解耦、多租戶隔離、動態遷移、原子備份與嚴謹的資安防護，並透過 Docker 與 CI/CD 流程提供了現代化、高可用之容器化發布方案。

### 8.2 未來展望
1. **即時推播管道擴充**：評估支援 Matrix 或 Web Push (PWA) 技術，提供完全去中心化之通知選擇。
2. **多看板歷史價格走勢圖表**：利用 SQLite 累積之行情資料，自動繪製特定硬體型號（如 RTX 4070）隨時間變化的價格折線圖，協助買家洞悉二手行情趨勢。
3. **邊緣裝置小模型本地推論**：探索於 Raspberry Pi 等單板電腦上透過 llama.cpp 運行量化小模型，進一步達成 100% 離線自給自足之純本地語意判讀。
