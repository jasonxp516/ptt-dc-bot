## 1. 審查結論與限制

最後一輪有界檢查未發現新的高影響問題，累計整理為 17 組修正項目（分頁不足與單輪 20 篇截斷合併列為 F02）。這不代表專案沒有其他問題，也不代表實際部署已通過驗證。

本次以靜態程式碼審查為主；環境沒有可用 Python interpreter，因此未執行 pytest、Python 最小重現、資料庫遷移或外部平台端到端測試。Telegram HTML 截斷另做過等價 JavaScript 字串運算，未呼叫 Telegram API。實作前需重查最新 commit，確認以下路徑與問題仍存在。

專案已有測試與 CI，並非從零建立驗證。本次讀到 16 個測試模組，CI 包含 Python 3.10–3.13 的 pytest 與售出判斷 benchmark；未在本機重新執行這些檢查。

最後補查範圍包括 SQL 動態片段、PTT URL／重新導向限制、SMTP 阻塞、互動按鈕授權及追蹤資料清理，本輪未確認其他高影響缺陷。這些結論不等於完整安全稽核。

## 4. 修改方案與交付順序

### 階段 A：修復可獨立處理的權限與狀態缺陷

**A1 — 管理權限（F05、F09）**

- 統一權限檢查入口，區分 bot owner 的全系統操作與指定管理者的訂閱範圍操作。
- Telegram 指令及 callback 均驗證操作者，不能只依 chat 對應到 subscriber 就放行。
- Discord 全系統管理僅允許 owner 名單，不以 `manage_channels` 推定系統管理權。
- AI 工具執行寫入前也套用同一授權規則。

**A2 — 看板生命週期與重複加入（F11、F13）**

- 看板是否仍被引用須包含暫停中的規則；移除自己的規則不能破壞別人的看板登記。
- 恢復訂閱時確認所需看板存在，修補舊資料中已遺失的登記。
- Slash 與 AI 加入看板共用同一個可重複呼叫的流程；既有板不能重建全域 seen 基準。
- 看板建立、初始化及巡檢的並行修改需有一致的交易／鎖定邊界。

**A3 — 取消安全與 AI 期限（F08、F07）**

- 先處理 gate 等待者取消、釋放交接及例外路徑，確保取消不會遺留鎖定狀態。
- 期限在工作提交時建立，包含排隊、模型切換、冷卻等待與 HTTP 請求。
- 每次請求使用剩餘時間，不能每換一個模型就重新取得完整期限。
- 互動 30 秒到期給明確回應；背景 120 秒到期則保留可重試工作，不宣稱判斷完成。
- 避免延遲回傳的結果重複寫入，或把 worker／future 留在永久等待狀態。

### 階段 B：建立持久處理與投遞流程

**B1 — 分開抓取、判斷、投遞進度（F01、F03）**

- 保留 SQLite，以持久資料表記錄判斷與通知工作，不引進外部訊息佇列。
- 全域「已抓取」不再代表所有訂閱者都已完成通知。
- 每個訂閱者／文章／平台各自記錄待判斷、待投遞、重試、成功及到期狀態；具體 schema 在實作時依現有結構最小化設計。
- AI 回傳至少區分命中、未命中、未完成；只有確定結果可完成判斷階段。
- 投遞明確回傳成功、暫時失敗或永久失敗，不再把所有失敗只壓成數字 0。
- 以唯一鍵防止同一次邏輯通知重複入列；工作與處理進度用交易維持一致。
- 重啟後恢復未完成工作；平台暫時錯誤退避重試，避免每輪密集重送。
- 文章發布滿 24 小時便停止 AI／投遞重試，保留原因並彙總告警。
- 外部平台已收件但本機尚未記錄就當機時，仍可能重送；遵守已接受的「少量重複優於漏報」，不承諾跨平台 exactly-once。

**B2 — 回補與訂閱時間界線（F02、F14）**

- 保存可恢復的看板進度，沿分頁回補至已知進度或文章超出 24 小時範圍。
- 請求上限／批次上限只限制本輪工作量，不能直接把未處理文章標為完成。
- 長回補可分輪續做；未能完成、遇到抓取限制或存在覆蓋缺口時告警。
- 訂閱／規則建立成功時持久記錄生效時間；新訂閱不推送發布早於生效時間的文章。
- 既有訂閱回補與新訂閱起點分別處理；新增使用者不改動其他人的進度。
- 統一使用可比較的文章發布時間，明確處理時區與舊資料遷移，不能以「首次看見時間」偷偷延長 24 小時期限。
- 發布時間解析失敗要可觀測，不能靜默當作已完成或任意放行。

### 階段 C：修復內容判斷與售出追蹤

**C1 — 商品與價格視角一致（F16）**

- 初次推播及售出追蹤共用商品識別流程，不把正向條件的最後一詞直接視為商品。
- 地區詞與商品詞的順序不能改變同一組 AND 條件的判斷結果。
- 多商品文章找不到目標價格時，不可直接取另一商品第一筆價格宣稱符合預算。
- 無法判定的商品／價格應有明確狀態；需要 AI 時沿用未完成工作的重試流程。

**C2 — 售出追蹤狀態與原始位置（F12、F15）**

- 更新卡片使用投遞記錄中的原始平台、channel／chat ID、message ID。
- 修改未來推播頻道不改寫已投遞卡片的位置。
- 區分販售中、洽談中／暫停收信、明確售出；暫時狀態不能設永久完成旗標。
- 在既有 18 小時追蹤窗內允許恢復販售與最終售出的更新，不因暫態重新延長追蹤期。
- 區分真正刪除訊息／失去權限與暫時平台錯誤，只有確定無法更新才終止該卡片追蹤。

**C3 — Telegram 格式與失敗隔離（F17）**

- 在原始內容層縮短，再產生平衡的 HTML；依最終內容檢查平台長度限制。
- 不在 HTML entity／標籤中間截斷，保留文章連結與基本識別資訊。
- 格式錯誤可改送受長度限制的純文字版本，仍失敗則交由持久重試流程處理。
- 一篇通知格式有誤不能阻斷同批其他文章。

### 階段 D：補齊可觀測性與本機恢復

**D1 — 健康、進度與告警（F06）**

- 分別記錄程序存活、巡檢進度及各看板最後成功抓取時間；沒有新文章不算抓取失敗。
- 各看板連續 10 分鐘抓取失敗時告警，恢復後通知一次，保留節流避免洗版。
- 沿用現有 owner DM／既有備援路徑，不另外引進監控服務；告警本身失敗至少留下可辨識日誌。
- AI／投遞到期以摘要呈現數量、平台、看板與原因，避免逐篇告警。
- 健康狀態不能只靠 heartbeat 宣稱抓取正常；外部服務故障與程序卡死需可區分，避免反覆重啟掩蓋問題。

**D2 — 備份成功語義與還原（F04）**

- 只有 SQLite 備份確實成功才記錄當日備份完成；整理與備份狀態避免互相誤用。
- 失敗記錄原因、退避重試並告警，保留前一份成功備份。
- 保留本機每日備份與至少七份成功備份；在暫存位置驗證可還原、資料可讀。
- 不增加異機、雲端、NAS 備份，不承諾整顆磁碟遺失時恢復。

### 階段 E：可延後的啟動支援

**E1 — 真正支援停用 Discord（F10）**

- 依平台開關驗證必要設定，停用 Discord 時不驗證其 token，也不執行 Discord 登入。
- 讓共用巡檢與其餘啟用平台有明確啟動入口，避免依賴 Discord ready 事件。
- 若持續以 Discord 為必要平台，本項可延後，不阻擋前述可靠性修復。

## 5. 必要驗收案例

下列為行為驗收目標，不要求建立與實作逐行對應的測試。優先用現有 pytest 架構、暫存 SQLite、可控制的時間與平台假介面；真實外部平台留給小範圍整合驗證。

| 對應 | 必須驗證的行為 |
| --- | --- |
| F01 | A 成功、B 暫時失敗：重啟後只續做 B；重複入列不產生多份邏輯工作。模擬平台成功後本機記錄失敗，確認不會永久漏報。 |
| F02 | 停機跨多頁、單輪超過 20 篇、請求上限分輪續做，都不把未處理文章誤標完成；超過 24 小時停止並告知缺口。 |
| F03、F07 | AI 429／逾時保留未完成狀態；排隊時間算入期限；切模型不重設期限；晚到結果不重複提交。 |
| F04 | 備份失敗後當日可重試，舊成功備份仍在；成功備份能在暫存資料庫還原並讀取設定與處理進度。 |
| F05、F09 | 一般成員、頻道管理員、指定訂閱管理者與 owner 的允許範圍正確；直接點 callback 或透過 AI 工具也不能繞過。 |
| F06 | 全部看板失敗但 heartbeat 仍更新時，業務降級可見；單一看板失敗只告警該板；成功抓取零篇新文算正常；恢復只通知一次。 |
| F08 | 取消第一個／中間／最後一個排隊者、交接時取消、請求例外後，其他等待者仍可取得 gate，無永久鎖定。 |
| F10 | 啟用 Discord 仍正常；停用 Discord 且無其 token 時，啟用的其餘平台與巡檢可啟動。 |
| F11 | 單人暫停非預設板超過 24 小時再恢復仍可掃描；A 暫停、B 移除同板不影響 A；舊資料缺看板登記可恢復。 |
| F12 | 推播 A 頻道後改到 B：舊卡仍在 A 更新，新通知送 B；暫時失敗不被當作訊息永久消失。 |
| F13 | AI 與 Slash 重複加入既有板皆不改動待處理新文；加入與 poll 並行時沒有全域進度重設。 |
| F14 | 建立成功前、後及恰好邊界的文章結果一致；新看板首輪不漏訂閱後新文；遷移舊規則不造成大量歷史推播。 |
| F15 | AVAILABLE → RESERVED → SOLD 與 AVAILABLE → RESERVED → AVAILABLE 均更新正確；18 小時到期才停止未結案追蹤。 |
| F16 | 無 AI：1060／1,000 元與 3060／6,000 元共存、預算 2,000 元時，`3060 台北` 與 `台北 3060` 都不得誤認 3060 符合預算；首次通知與追蹤選到同一商品。 |
| F17 | 長文、`&<>`、emoji、HTML 標籤邊界與大量規則下輸出有效；格式失敗有純文字備援；單篇失敗不阻斷下一篇。 |
| Q12 | AI 與通知在文章發布滿 24 小時後不再執行，摘要只計入應告知的到期失敗，重啟不重複洗版。 |

## 6. 遷移、部署與回復安排

1. 核對最新原始碼與既有測試；先建立目前版本的測試基準，再為本次缺陷加入可重現案例。F08 必須先用 Python 確認取消行為。
2. 修改 schema 前建立並驗證一份本機 SQLite 備份；遷移使用版本控制，盡量採新增欄位／表，避免同次大幅改寫既有資料。
3. 訂閱生效時間、既有 seen 與 delivery 資料的遷移需有明確規則：不把所有已處理文章重新變成待推播，也不偽造過去失敗通知。舊版已永久漏報且沒有足夠紀錄者，無法承諾完整補回。
4. 階段 A 可拆成小變更驗收；階段 B 的持久工作、訂閱界線與回補需一起驗證資料一致性。F13 的緊急修正可先獨立阻止既有看板重建基準。
5. 執行相關測試、完整 pytest 與既有售出 benchmark；檢查 CI 支援的 Python 版本，不僅驗證單一版本。
6. 在測試頻道驗證一篇新文、平台暫時失敗、重啟續做、到期摘要、改頻道後更新舊卡，以及一次備份還原。外部平台測試使用者需提供實際可用設定，但不能把憑證寫入計畫或日誌。
7. 部署前停寫並保存當時 DB；回退程式時確認 schema 相容。若還原舊備份，須揭露還原點後設定、進度與投遞記錄的損失，以及可能重複通知，不能直接覆寫運行中的 DB。

## 7. 實作時需補齊的細節

以下尚未在訪談中逐項確認，列為建議預設，不當作使用者已同意的需求；不阻礙先修權限、看板登記、gate 與錯誤價格等既有缺陷。

- 暫停期間：建議停止發送，已存在的工作保留至原 24 小時期限；恢復不重設文章年齡。
- 刪除訂閱／規則：建議取消尚未送出的相關工作，保留必要稽核與已投遞卡片的位置紀錄。
- 修改規則／預算後，尚未送出的文章採新條件重評或保留原條件：需在持久工作實作前確認，並用規則版本避免結果混用。
- 價格／商品無法確定時：建議保留未知狀態，不直接宣稱符合預算；若要標示未知後仍推播，需另確認通知偏好。
- owner 名單、指定管理者範圍及實際告警目的地：部署時填入，沿用既有設定可用部分，不在文件中假設帳號或頻道 ID。
- 舊訂閱生效時間缺資料：遷移策略需避免同時造成歷史洗版與把所有舊訂閱當全新訂閱，完成前不得直接上線。
